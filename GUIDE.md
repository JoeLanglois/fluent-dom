# Building interfaces with `$`

A guide to building user interfaces with the `$` library, from a three-line
script that enhances a server-rendered page to a full single-page application.

> Implementation: `src/fluent-dom.js` in this repository (single file,
> JSDoc-typed, `dist/fluent-dom.d.ts` generated by `tsc`). This guide is
> the usage documentation for that implementation.

The library is deliberately small. It does not render your app for you, it does
not hold your state, and it does not talk to the network. It gives you three
things and nothing else:

1. **`$`** — select and wrap DOM elements, then get and set things on them
   fluently.
2. **`$.el`** — create DOM elements fluently, safely, without parsing HTML
   strings.
3. **`$.events`** — turn a plain object into an event emitter, so parts of an
   interface can talk to each other without reaching into each other's DOM.

Everything in this guide, including the SPA at the end, is built from those
three pieces, plus native `fetch`, native `history` / `location`, and plain
JavaScript functions. When a pattern appears in this guide (a store, a router,
a component), it is a *recipe* written with the library, not a feature hidden
inside it. That is the point: you can read every line of what runs your app.

---

## 1. The mental model

### 1.1 A wrapper around elements

`$` always returns the same kind of object, a *wrapper*, whether it matched
zero, one, or a hundred elements.

```js
$('#save')          // wrapper around the matching elements
$(element)          // wrap one element you already have
$(nodeList)         // wrap a NodeList or an array of elements
```

The contract that makes chaining predictable:

- **Setters apply to every element in the wrapper and return the wrapper**,
  so calls chain.
- **Getters read from the first element and return a value**, so they end a
  chain.
- **An empty wrapper is safe.** Setters no-op, getters return `undefined`.
  You do not need to null-check a selection before using it.
- The wrapper is iterable and has `.length`. The raw element is always one
  hop away: `$('#save')[0]` or `$('#save').el`. Drop to the raw element
  whenever a native API is clearer; wrapping again is free: `$($('#save')[0])`.

### 1.2 Strings are text, except in one place

This is the safety rule of the whole library, and it is structural, not a
sanitizer you have to remember to call:

- Every string you pass to the API becomes **text**: `.text(str)`, a string
  child of `$.el`, `.append(str)`. It can never become markup.
- The **only** way a string becomes markup is `.html(str)` (or the `html:`
  key in `$.el` props). Treat that as developer-authored markup only: layout
  skeletons, icons, static structure. **Never feed user data to `.html()`.**
  User data always travels through `.text()`, `.val()`, and `.attr()`.

Audit rule: grep your codebase for `.html(` and `html:` and you have found
every markup sink. If none of them touches user input, user input cannot
produce DOM XSS through this library.

Attribute safety follows the same spirit: `on*` attributes cannot be set
through `.attr()` (use `.on()`), and URL attributes (`href`, `src`,
`action`, `formaction`) reject `javascript:` and `data:text/html` values.

### 1.3 No network, no magic

There is no ajax helper. Use `fetch`; it is enough, and its promises compose
better than a wrapper ever did. There are no animations, no effects, no
deferreds, no reactive system. State lives in your objects, rendering is
your functions, and updates happen because your code calls a function, not
because a framework noticed something.

That means the discipline in this guide matters: small render functions,
one place where state changes, and events (`$.events`) between parts that
should not know each other's DOM.

### 1.4 Setup

```html
<script type="module">
  import { $ } from './fluent-dom.js'

  // your code here; the DOM above the script already exists,
  // and modules are deferred by default, so no ready wrapper is needed
</script>
```

One file, ES module, no build step required to use it, no dependencies.

## 2. Level 1 — Enhance existing HTML

The smallest useful job: the server (or a static page) already rendered the
HTML, and you add a bit of behaviour. This is most real-world JavaScript.

### 2.1 Get and set

```js
// text: getter reads the first, setter writes all
const title = $('h1').text()
$('h1').text('Invoices')

// values, for form fields
const email = $('#email').val()
$('#email').val('a@example.com')

// attributes and properties
$('#avatar').attr('src', url)
const href = $('a.download').attr('href')
$('#agree').prop('checked', true)

// classes and styles
$('.card').addClass('highlight')
$('#panel').toggleClass('open')
const open = $('#panel').hasClass('open')
$('#box').css('margin-top', '1rem')
$('#box').css({ color: 'red', opacity: '0.8' })
```

Getters and setters are the same method name; the argument count decides.
That is the jQuery convention, kept because it makes short scripts short.

### 2.2 Events

```js
$('#save').on('click', (e) => { /* ... */ })

// several events at once, from an object
$('#name').on({
  input:  (e) => validate(),
  blur:   (e) => showErrors(),
})

// delegation: one listener for children that come and go
$('#list').on('click', '.delete', function (e) {
  $(this).closest('li').remove()
})

// removal: .off(name, fn) for one handler, .off() for all of them
$('#save').off('click', handler)
```

Inside a handler, `this` is the element the handler is attached to (for
delegation, the matched child), and the argument is the native event. There
is no wrapped event object to learn.

### 2.3 Traversal

```js
$('#list').find('li.active')       // descendants matching a selector
$('li').filter('.done')            // keep matching
$('li').not('.done')               // drop matching
$('li').eq(2)                      // one element, by index, as a wrapper
$('li').first().addClass('top')
$(el).closest('form')              // nearest matching ancestor (or self)
$(el).parent()
$(el).children()
$(el).siblings()
```

**Recipe: the confirm button.** Almost every "small enhancement" is a
variation of this shape: read something, change something, react to a click.

```js
$('#delete-account').on('click', () => {
  const $btn = $('#delete-account')
  if ($btn.text() !== 'Are you sure?') {
    $btn.text('Are you sure?').addClass('danger')
    return
  }
  // second click: do the thing
})
```

No state library, no component. If your whole page needs three of these,
stop here; the rest of the guide would be overhead.

## 3. Level 2 — Create elements

When JavaScript has to produce DOM that the server did not render, use
`$.el`. It never parses an HTML string, so the structure you write is the
structure you get, and every string in it is text.

### 3.1 The builder

```js
$.el('button')
  .addClass('primary')
  .attr('type', 'button')
  .text('Save')
  .on('click', save)
  .appendTo('#toolbar')
```

### 3.2 Declarative creation for nested structure

Pure chaining is unreadable for trees, so `$.el` also takes props and
children up front:

```js
const $list = $.el('ul', { class: 'items' },
  items.map(item =>
    $.el('li', { 'data-id': item.id },
      $.el('span', { class: 'name', text: item.name }),
      $.el('button', { class: 'delete', text: '×' }),
    )
  )
)
```

- The props object reserves a few keys: `text`, `class`, `html` (trusted
  markup only, see §1.2), `style` (object), `dataset` (object), `on`
  (event map), and `ref` (see §4.2). Every other key is set as an attribute.
- Children may be elements, wrappers, strings (text), arrays (flattened,
  so `.map` results drop in directly), and `null` / `false` (skipped, so
  conditionals inline cleanly):

```js
$.el('div', { class: 'card' },
  $.el('h2', { text: user.name }),
  user.admin && $.el('span', { class: 'badge', text: 'admin' }),
  $.el('p', { text: user.bio }),
)
```

### 3.3 Static skeletons with `.html()`

For a chunk of fixed structure, writing fifteen `$.el` calls is noise.
Use the one trusted sink for the skeleton, then fill the variable parts
with safe calls:

```js
const $form = $.el('form').html(`
  <label>Email <input ref="email" type="email" required></label>
  <label>Name  <input ref="name" type="text"></label>
  <p ref="error" class="error" hidden></p>
  <button ref="submit" type="submit">Save</button>
`)
// variable / user-derived values only ever go through .val() / .text()
```

Note the `ref` attributes in the markup. They are the bridge to the next
level.

### 3.4 Manipulation

```js
$list.append($item)            // also: prepend, before, after
$item.replaceWith($other)
$item.remove()
$list.empty()                  // remove all children, keep the element
const $copy = $item.clone()
```

Appending a wrapper moves its elements (standard DOM behaviour). Appending
a string appends a text node, never markup.

## 4. Level 3 — Components as functions

Past a few hundred lines, "select things by global selector" stops scaling:
selectors collide, and you cannot tell which code owns which part of the
page. The step up is the oldest one in programming: a function that builds
a piece of interface, keeps references to its own parts, and returns a
wrapper.

There is no component class and no registration. A component is a function
with a convention:

- It **builds its own root element** (with `$.el` and/or a trusted `.html()`
  skeleton).
- It **grabs its internal parts once**, with `refs()`.
- It **wires its own events**.
- It **returns an object** exposing the root (`$el`) and whatever methods
  the outside world legitimately needs, and nothing else.

### 4.1 A first component

```js
function Counter() {
  const $root = $.el('div', { class: 'counter' }).html(`
    <button ref="minus" type="button">−</button>
    <span ref="value">0</span>
    <button ref="plus" type="button">+</button>
  `)
  const refs = $root.refs()

  let count = 0
  const render = () => refs.value.text(String(count))

  refs.minus.on('click', () => { count--; render() })
  refs.plus.on('click',  () => { count++; render() })

  return { $el: $root }
}

$('#app').append(Counter().$el, Counter().$el)  // two independent counters
```

Two instances share nothing. All state (`count`) is a local variable, all
DOM access goes through `refs`, and the outside world can only place the
root element. This pattern alone carries surprisingly far.

### 4.2 `refs()` in detail

`refs()` walks a wrapper's elements and their descendants and returns an
object whose keys are the values of `ref` attributes and whose values are
single-element wrappers:

```js
const refs = $form.refs()
// { email: $(<input>), name: $(<input>), submit: $(<button>) }

refs.email.val()
refs.submit.on('click', save).addClass('busy')
```

`refs()` also accepts a handlers object. Each key is a ref name, each
value a function that receives that ref's wrapper as its first argument
(and as `this`), plus the ref name as its second argument, so a part can
be configured inline at the moment you collect it. The refs object is
still returned, so both styles compose:

```js
const refs = $form.refs({
  label:  (l) => l.text('Click Me'),
  email:  (e) => e.val(prefill).on('input', validate),
  submit: (b) => b.on('click', save),
})
refs.email.el.focus()
```

A handler for a ref that does not exist is still called, with an empty
wrapper, whose setters no-op like any empty wrapper. A handler value
that is not a function throws a `TypeError`.

Rules worth knowing:

- A ref is set like any attribute: `ref="email"` in markup, or
  `{ ref: 'email' }` in `$.el` props.
- The search includes the root element itself if it carries a `ref`.
- It works on detached trees, so a component can collect its refs before
  it is appended anywhere.
- It is a **snapshot**, computed when you call it, not a live view. After
  you change the subtree (`.html()`, append, remove, or a server-driven
  morph of the subtree), call `refs()` again.
- Ref names should be unique within the subtree. If two elements carry the
  same ref, the last one in document order wins. Repeated things are a
  class or a selector query, not a ref.
- Refs are for a component's *own* internals. Reaching into another
  component's refs from outside breaks the one useful boundary this
  pattern gives you; expose a method instead.

### 4.3 Exposing an API, handling teardown

```js
function SearchBox({ onSearch }) {
  const $root = $.el('div', { class: 'search' }).html(`
    <input ref="input" type="search" placeholder="Search…">
    <button ref="clear" type="button" hidden>Clear</button>
  `)
  const refs = $root.refs()

  refs.input.on('input', () => {
    refs.clear.prop('hidden', refs.input.val() === '')
    onSearch(refs.input.val())
  })
  refs.clear.on('click', () => {
    refs.input.val('').el.focus()
    onSearch('')
  })

  return {
    $el: $root,
    focus: () => refs.input.el.focus(),
    destroy: () => { $root.off().remove() },
  }
}
```

Two details in that example generalise:

- **Callbacks in, methods out.** A component reports happenings through
  callback props (`onSearch`) and accepts commands through returned
  methods (`focus`). It never queries the page for its parent.
- **`destroy()` is your responsibility.** `.off()` removes the wrapper's
  listeners and `.remove()` detaches the root. If a component registered
  listeners *outside* its root (on `window`, on a shared events object),
  `destroy()` must unregister those too. Interfaces that add and remove
  pieces constantly, like the SPA in §8, live or die by this.

## 5. Level 4 — State and rendering

A component with a couple of local variables manages itself. The moment
several components must agree about the same data (a list, a filter, and a
counter that must never disagree), local variables stop working. You need
one place where state lives, and a rule for how state becomes DOM.

### 5.1 The store recipe: `$.events` on a plain object

`$.events(obj)` adds `on` / `once` / `off` / `emit` to any plain object,
in place, and returns the same object. Listeners are stored outside the
object (in a `WeakMap`), so they never pollute its keys or its JSON, and
the same handler registered twice for one event is stored once.

```js
const store = $.events({
  items: [],
  filter: 'all',

  add(item) {
    this.items.push(item)
    this.emit('change')
  },
  remove(id) {
    this.items = this.items.filter(i => i.id !== id)
    this.emit('change')
  },
  setFilter(filter) {
    this.filter = filter
    this.emit('change')
  },
  visible() {
    return this.filter === 'all'
      ? this.items
      : this.items.filter(i => i.status === this.filter)
  },
})
```

The conventions that keep this sane:

- **State changes only inside the object's own methods**, and every method
  that changes state ends by emitting. Nobody outside assigns
  `store.items = ...` directly.
- **One coarse event is the default.** A single `'change'` is easier to
  reason about than ten fine-grained events, and at the scale this library
  targets, re-rendering a subtree on every change is cheap. Add a named
  event (`'selection'`, `'error'`) only when a subscriber provably should
  not run on every change.
- Handlers receive exactly the arguments passed to `emit`, and `this` is
  the object. No event object is fabricated.

The same `on` name works for DOM events and store events, and the map
form works for both:

```js
store.on({ change: render, error: showError })
```

### 5.2 Rendering: two strategies, choose per subtree

**Strategy A, re-render the subtree.** A render function rebuilds a
container's contents from state. Simple, always consistent, and the right
default for small to medium subtrees:

```js
function renderList() {
  refs.list.empty().append(
    store.visible().map(item =>
      $.el('li', { 'data-id': item.id, class: item.done ? 'done' : '' },
        $.el('span', { text: item.title }),
      )
    )
  )
  refs.count.text(`${store.items.length} items`)
}

store.on('change', renderList)
```

Rebuilding discards DOM state inside the subtree: focus, text selection,
scroll position of inner elements, in-progress typing. So:

**Strategy B, targeted updates.** Keep the elements, change only what the
state change actually touched. This is what `refs()` and traversal are
for, and it is the right choice for the subtree the user is interacting
with right now:

```js
// a checkbox toggled: update the row, do not rebuild the list
$list.on('change', '.toggle', function () {
  const $row = $(this).closest('li')
  store.setDone($row.attr('data-id'), $(this).prop('checked'))
  $row.toggleClass('done', $(this).prop('checked'))
  refs.count.text(`${store.remaining()} remaining`)
})
```

The rule of thumb: re-render subtrees the user is *looking at*, update in
place the subtree the user is *touching*. A page is usually one of each.

### 5.3 Lists that change

Three list patterns cover most cases, in increasing order of effort:

1. **Rebuild on change** (§5.2 A). Default. Fine into the hundreds of rows.
2. **Append / remove one row** for the common single-item change, with a
   full rebuild as the fallback for anything unusual (filter change,
   reorder, bulk load). Keeps typing and scroll untouched in the common
   case without giving up the simple path.
3. **Keyed update:** find the existing row by its key and patch it, so
   element identity (and focus) survives:

```js
function upsertRow(item) {
  const existing = refs.list.find(`[data-id="${item.id}"]`)
  if (existing.length) {
    existing.find('.title').text(item.title)
    existing.toggleClass('done', item.done)
  } else {
    refs.list.append(rowFor(item))
  }
}
```

Note the key lives in a `data-id` attribute, set at creation and read back
with `.attr('data-id')`. Keys are data, not refs: there are many rows, and
refs are for unique named parts.

### 5.4 Forms

Forms are where the get/set API earns its keep:

```js
function ItemForm({ onAdd }) {
  const $root = $.el('form').html(`
    <input ref="title" type="text" placeholder="New item" required>
    <p ref="error" class="error" hidden></p>
    <button type="submit">Add</button>
  `)
  const refs = $root.refs()

  $root.on('submit', (e) => {
    e.preventDefault()
    const title = refs.title.val().trim()
    if (!title) {
      refs.error.text('Title is required').prop('hidden', false)
      refs.title.el.focus()
      return
    }
    refs.error.prop('hidden', true)
    onAdd(title)
    refs.title.val('')
  })

  return { $el: $root }
}
```

Patterns to copy: `preventDefault` and stay on the page; validate at
submit and show the error in a ref'd element that already exists in the
skeleton (no creating error DOM on the fly); clear or preserve the input
deliberately after success; put focus back where the user's hands are.
For server-backed forms, disable the submit button while the request is
in flight and re-enable it in a `finally`, so a double-click cannot submit
twice.

## 6. Level 5 — Data from the network

The library has no opinion about the network, so this level is mostly
discipline around `fetch`, expressed in the vocabulary you already have:
a store holds the data, components render loading / error / content.

### 6.1 A data module, not scattered fetches

Put every request for one resource in one small module that owns the
store for it. Components call its methods and subscribe to its changes;
they never call `fetch` themselves.

```js
const todos = $.events({
  items: [],
  status: 'idle',        // 'idle' | 'loading' | 'error' | 'ready'
  error: null,

  async load() {
    this.status = 'loading'; this.emit('change')
    try {
      const res = await fetch('/api/todos')
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      this.items = await res.json()
      this.status = 'ready'
    } catch (err) {
      this.status = 'error'; this.error = err
    }
    this.emit('change')
  },

  async add(title) {
    const res = await fetch('/api/todos', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ title }),
    })
    if (!res.ok) throw new Error(`HTTP ${res.status}`)
    this.items.push(await res.json())
    this.emit('change')
  },
})
```

### 6.2 Rendering the three states

Because the store emits on every transition, one render function covers
loading, error, and content without any component knowing a request
happened:

```js
function render() {
  refs.spinner.prop('hidden', todos.status !== 'loading')
  refs.error.prop('hidden', todos.status !== 'error')
    .text(todos.status === 'error' ? `Could not load: ${todos.error.message}` : '')
  refs.list.prop('hidden', todos.status !== 'ready')
  if (todos.status === 'ready') renderList()
}
todos.on('change', render)
todos.load()
```

Notes that matter in practice:

- **Error text goes through `.text()`**, always. An error message can
  contain anything the server or the network produced.
- **Optimistic updates are a store decision**, not a rendering trick: add
  the item locally, emit, then replace or roll back when the request
  resolves. Keep the rollback in the same method that was optimistic.
- **Race conditions are yours to handle**, and the simple tool is a
  sequence number in the store: each `load()` captures `++this.seq` and
  only applies its result if it is still the latest.

## 7. Level 6 — Several components, one page

At this scale the risk is not rendering, it is coupling: components that
query each other's DOM, or a page script that knows every component's
internals. Two rules prevent it:

1. **Components own their DOM.** Nobody outside a component selects inside
   it. Communication is callbacks in, methods out (§4.3), or a shared
   store (§5.1).
2. **Shared state lives in a store, not in a component.** If two
   components need it, it does not belong to either of them.

### 7.1 Composition

A page is a component whose children happen to be components:

```js
function TodoPage() {
  const $root = $.el('main', { class: 'todo-page' }).html(`
    <h1>Todos</h1>
    <div ref="form"></div>
    <div ref="filters"></div>
    <p ref="count"></p>
    <ul ref="list"></ul>
  `)
  const refs = $root.refs()

  refs.form.append(ItemForm({ onAdd: (title) => todos.add(title) }).$el)
  refs.filters.append(Filters({
    onFilter: (f) => todos.setFilter(f),
  }).$el)

  const render = () => { /* §5.2, using refs.list and refs.count */ }
  todos.on('change', render)
  render()

  return {
    $el: $root,
    destroy: () => { todos.off('change', render); $root.remove() },
  }
}
```

Note `destroy()` unsubscribing from the store. A page component that is
removed without unsubscribing keeps rendering into detached DOM forever:
invisible, and a leak.

### 7.2 When components must talk without a store

If exactly two components need to coordinate and a store is overkill
(a dialog and the button that opens it), pass a shared emitter:

```js
const bus = $.events()
bus.on('dialog:open', (id) => dialog.open(id))
```

Treat the bus as a last resort, and name events like `dialog:open`, with
the owner first. A bus with forty anonymous events is a store that lost
its state; if you find yourself there, go back to §5.1 and give the state
a home.

## 8. Level 7 — A single-page application

An SPA adds exactly three things to §7: a **router** (URL ↔ which page
component is shown), **navigation** without page loads, and **disciplined
teardown** (the old page is destroyed, not hidden, unless you deliberately
keep it alive). Everything else is the patterns you already have.

The library ships no router, on purpose: a router is about thirty lines
once you decide your conventions, and your conventions (hash vs. history,
route syntax, guards) are yours. Here is the recipe.

### 8.1 A minimal history router as an events object

```js
const router = $.events({
  route: null,           // { name, params }

  start() {
    window.addEventListener('popstate', () => this.sync())
    this.sync()
  },
  sync() {
    this.route = parse(location.pathname)
    this.emit('route', this.route)
  },
  go(path) {
    history.pushState(null, '', path)
    this.sync()
  },
})

function parse(path) {
  if (path === '/' || path === '/todos') return { name: 'todos', params: {} }
  const m = path.match(/^\/todos\/(\d+)$/)
  if (m) return { name: 'todo-detail', params: { id: m[1] } }
  return { name: 'not-found', params: {} }
}
```

Interception of link clicks is one delegated listener for the whole app:

```js
$('body').on('click', 'a[data-route]', function (e) {
  e.preventDefault()
  router.go($(this).attr('href'))
})
```

Links stay real links (`href` is correct, open-in-new-tab works if you
let non-left / modified clicks fall through), and only clicks you handle
become SPA navigation. If your deployment cannot rewrite URLs to your
entry page, use the same recipe with `location.hash` and the `hashchange`
event instead; nothing else in this section changes.

### 8.2 The app shell

The shell is a component that never unmounts. It owns the persistent
chrome (header, nav) and a single outlet where pages come and go:

```js
function App() {
  const $root = $.el('div', { class: 'app' }).html(`
    <header>
      <nav>
        <a href="/todos" data-route>Todos</a>
        <a href="/about" data-route>About</a>
      </nav>
    </header>
    <div ref="outlet"></div>
  `)
  const refs = $root.refs()

  let current = null     // the mounted page: { $el, destroy }

  const pages = {
    'todos':       () => TodoPage(),
    'todo-detail': (route) => TodoDetailPage({ id: route.params.id }),
    'about':       () => AboutPage(),
    'not-found':   () => NotFoundPage(),
  }

  router.on('route', (route) => {
    current?.destroy()
    current = pages[route.name](route)
    refs.outlet.empty().append(current.$el)
  })

  return { $el: $root }
}

$('#app').append(App().$el)
router.start()
```

The lifecycle rule is absolute: **mounting a page destroys the previous
one.** `destroy()` unsubscribes from stores and the router, removes
listeners, and detaches DOM (§4.3, §7.1). If a page is expensive and
genuinely worth keeping alive (a half-filled long form), hide it instead
of destroying it, but say so in its name or a comment; silent caching of
pages is how SPAs grow stale-state bugs.

### 8.3 A complete example, assembled

Putting every level together, a small but complete SPA: a todo app with a
list page, a detail page, a store backed by `fetch`, and routing.

```js
import { $ } from './fluent-dom.js'

// ---- store (§5.1, §6.1) ---------------------------------------------
const todos = $.events({
  items: [], status: 'idle', error: null,
  async load() { /* §6.1 */ },
  async add(title) { /* §6.1 */ },
  async toggle(id) {
    const item = this.items.find(i => i.id === id)
    item.done = !item.done
    this.emit('change')
    // persist in the background; roll back on failure
    const res = await fetch(`/api/todos/${id}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ done: item.done }),
    })
    if (!res.ok) { item.done = !item.done; this.emit('change') }
  },
  byId(id) { return this.items.find(i => i.id === id) },
})

// ---- router (§8.1) ----------------------------------------------------
// router and parse as in §8.1

// ---- components (§4, §5.4) -------------------------------------------
function ItemForm({ onAdd }) { /* §5.4 */ }

function TodoPage() {
  const $root = $.el('main').html(`
    <h1>Todos</h1>
    <div ref="form"></div>
    <p ref="status"></p>
    <ul ref="list"></ul>
  `)
  const refs = $root.refs()
  refs.form.append(ItemForm({ onAdd: (t) => todos.add(t) }).$el)

  refs.list.on('change', '.toggle', function () {
    todos.toggle($(this).closest('li').attr('data-id'))
  })
  refs.list.on('click', '.title', function () {
    router.go(`/todos/${$(this).closest('li').attr('data-id')}`)
  })

  const render = () => {
    refs.status.text(
      todos.status === 'loading' ? 'Loading…' :
      todos.status === 'error'   ? `Error: ${todos.error.message}` : '')
    refs.list.empty().append(todos.items.map(item =>
      $.el('li', { 'data-id': item.id, class: item.done ? 'done' : '' },
        $.el('input', { type: 'checkbox', class: 'toggle' })
          .prop('checked', item.done),
        $.el('span', { class: 'title', text: item.title }),
      )))
  }
  todos.on('change', render)
  render()
  if (todos.status === 'idle') todos.load()

  return { $el: $root, destroy: () => { todos.off('change', render); $root.remove() } }
}

function TodoDetailPage({ id }) {
  const item = todos.byId(id)
  const $root = $.el('main').html(`
    <a href="/todos" data-route>← All todos</a>
    <h1 ref="title"></h1>
    <p ref="state"></p>
  `)
  const refs = $root.refs()
  refs.title.text(item ? item.title : 'Not found')
  refs.state.text(item ? (item.done ? 'Done' : 'Open') : '')
  return { $el: $root, destroy: () => $root.remove() }
}

// ---- shell (§8.2) ------------------------------------------------------
// App as in §8.2, with pages = { todos, 'todo-detail', ... }

$('#app').append(App().$el)
router.start()
```

Read top to bottom, that file uses every idea in this guide exactly once:
stores own state and network, components own DOM, refs stay inside their
component, the router is an emitter, the shell destroys pages on
navigation, and user data (`item.title`, error messages) only ever flows
through `.text()`.

### 8.4 Growing past one file

When the SPA outgrows a single module, split by role, not by library
feature. No build step is required; native ES modules are the bundler
until you want one.

```text
app/
  main.js        imports $, builds App, starts the router
  router.js      the §8.1 recipe
  stores/
    todos.js     the §6.1 data module
  components/
    item-form.js
    filters.js
  pages/
    todo-page.js
    todo-detail-page.js
    about-page.js
```

Each file exports one function or one store. If a file needs to import a
component's internals rather than its exported function, the boundary was
drawn in the wrong place; move the shared thing into a store.

### 8.5 Persistence and auth, briefly

- **Local persistence:** a store that serialises itself is ten lines:
  subscribe to its own `'change'`, write `JSON.stringify(this.items)` to
  `localStorage`, and hydrate in an `init()` before the first render.
  Persist data, never DOM.
- **Auth:** keep the token in one module, attach it in that module's
  `fetch` calls (§6.1 is the only place requests happen, which is why),
  and model "logged out" as a route: on a 401, the data module emits an
  `'unauthorized'` event and the shell routes to a login page like any
  other page.

## 9. Patterns and anti-patterns

**Do**

- One store per resource; components subscribe and render.
- Re-render subtrees the user is looking at; update in place the subtree
  the user is touching (§5.2).
- Collect `refs()` once per component, right after building its root.
- Give every mountable thing a `destroy()`, and call it.
- Keep render functions pure with respect to the DOM outside their own
  subtree: read state, write own DOM, nothing else.

**Avoid**

- Selecting inside another component, or keeping global selectors for
  things a component owns. That is what refs are for.
- Feeding anything user-derived to `.html()`, including error messages,
  URL parameters, and "trusted" API fields. Trust is not transitive.
- Emitting fine-grained events preemptively. Start with `'change'`; split
  only when a real subscriber needs it.
- Hiding pages instead of destroying them, without an explicit reason.
- Storing state in the DOM (reading your own app state back out of
  `.text()` or attributes). The DOM is output. State lives in objects;
  if you need a value, it should already be in the store.
- Reaching for a bus (§7.2) before a store. Events without state are how
  apps become impossible to debug: prefer state you can inspect.

## 10. API quick reference

### Selection and wrapping

| Call | Meaning |
| --- | --- |
| `$(selector, root?)` | Wrap elements matching a selector |
| `$(element \| NodeList \| array \| wrapper)` | Wrap what you already have |
| `$el` / `[0]` | First raw element |
| `.length`, iteration | Size, and `for...of` / spread support |

### Creation

| Call | Meaning |
| --- | --- |
| `$.el(tag, props?, ...children)` | Create an element; strings are text, `null`/`false` skipped, arrays flattened |
| Reserved props | `text`, `class`, `html` (trusted only), `style`, `dataset`, `on`, `ref` |

### Get / set (getter = no value argument, reads first; setter = all, chains)

`text()`, `html()` (trusted markup only), `val()`, `attr(name[, value])`,
`removeAttr(name)`, `prop(name[, value])`, `css(name[, value])` /
`css(object)`, `data` via native `dataset` semantics,
`addClass`, `removeClass`, `toggleClass`, `hasClass`.

### Traversal and manipulation

`find`, `closest`, `parent`, `parents`, `children`, `siblings`, `next`,
`prev`, `filter`, `not`, `eq`, `first`, `last`, `slice`,
`append`, `prepend`, `before`, `after`, `appendTo`, `replaceWith`,
`remove`, `empty`, `clone`.

### Events (DOM)

`on(name, handler)`, `on(name, selector, handler)` for delegation,
`on(map)`, `one(name, handler)`, `off([name[, handler]])`.

### Refs

`refs()` → `{ [refName]: wrapper }`, snapshot, self + descendants,
single-element wrappers, last duplicate wins.
`refs({ [refName]: (wrapper, name) => void })` → same object, after
calling each handler with its ref's wrapper (empty wrapper if missing).

### Events (plain objects)

`$.events(obj?)` → the same object, augmented with `on(name, handler)`,
`on(map)`, `once(name, handler)`, `off([name[, handler]])`,
`emit(name, ...args)`.

## 11. Checklist: starting a new interface

1. Is it an enhancement of server HTML? Stop at §2.
2. Does JavaScript create DOM? Use `$.el`; reserve `.html()` for static
   skeletons (§3).
3. Is a piece reused, or does it own internal parts? Make it a component
   function with `refs()` (§4).
4. Must several pieces agree on data? Give the data a store (§5.1) and
   pick a render strategy per subtree (§5.2).
5. Does data come from the network? One data module per resource, three
   rendered states (§6).
6. More than one screen? Add the router recipe and a shell that destroys
   pages on navigation (§8).
7. Before shipping: grep for `.html(` and confirm every call site is
   developer-authored markup only (§1.2).
